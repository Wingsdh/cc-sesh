# cc-sesh picker 状态表留白 + session 折叠展开 + 右侧预览分栏 · 验收用例

## 0. 用例说明

### 被测范围

cc-sesh picker（本地终端 TUI，Go + bubbletea）的三块改造：

1. Claude 状态表左右留白（徽章区左内缩 / 右间隔）
2. session 折叠展开 + window 行 + 右侧预览分栏（含 window 行回车直达、搜索匹配 window 名、折叠状态记忆）
3. 相关存量按键与数据流不回归

### 测试环境

仅 **macOS 终端 + tmux** 一个端。picker 是本地 CLI TUI，不是 App / Web，不存在多端概念。

- 构建：`just build`（产物 `$(go env GOPATH)/bin/cc-sesh`）
- 入口：`cc-sesh picker`（别名 `pick` / `pk`）
- 交叉核对子命令：`cc-sesh window`（列 / 切 window）、`cc-sesh preview`（抓屏）

### 两类用例与验证方式

- **A 类（可自动化）**：针对可见行构建、展开集合运算、留白常量、预览状态机、connector 判定、持久化读写、返回值构造、搜索匹配、ANSI 渲染等纯逻辑 / 数据契约，用「给定输入 → 期望输出」描述，供开发对照编写 Go 单元测试；不依赖真实终端渲染，QA 通过比对开发测试的断言结果核实，不要求人工操作终端。
- **B 类（只能手工验）**：涉及真实终端视觉呈现、真实 tmux 交互时序、跨进程持久化效果的场景，QA 需要在真机终端上按前置条件搭建 fixture、执行操作、肉眼核对判定标准；必要时用 `cc-sesh window` / `cc-sesh preview` 交叉核对预期值。

### 判定基线速查表

| 项                                            | 数值                                                                 | 来源                  |
| --------------------------------------------- | -------------------------------------------------------------------- | --------------------- |
| 徽章区左内缩（ATTN 首字符与左侧内容间距）     | ≥ 2 空格                                                             | PRD 留白规则表 / 详设 |
| 徽章区右间隔（WAIT 末字符与会话名首字符间距） | ≥ 3 空格（现为 1）                                                   | PRD 留白规则表 / 详设 |
| 列表区宽度上限                                | 60 列                                                                | 详设·预览分栏         |
| 列表区与预览区分隔间距                        | 2 列                                                                 | 详设                  |
| 预览区宽度下限                                | 40 列                                                                | 详设                  |
| 预览显示阈值（终端总宽）                      | ≥ 102 列（60+2+40，PRD 基线 100 的精确化）                           | 详设 / brief          |
| 取快照防抖时长                                | 光标停留 150ms                                                       | PRD / 详设            |
| Enter 在 window 行的返回值格式                | `会话名:window序号`                                                  | 详设                  |
| connector window 策略认领条件                 | 4 条全部满足才认领                                                   | 详设                  |
| 会话可展开判定                                | 来源为 tmux 且 window 数 ≥ 1                                         | 详设                  |
| 折叠记忆文件内容格式                          | `{"version":1,"expanded":[...]}`，独立 JSON 文件，与 ATTN 存储分文件 | 详设                  |

### 复现用 fixture 清单

以下 fixture 均可用 `tmux new-session -d -s <名>`、`tmux new-window -t <名>` 搭建，在指定 window 内跑 `claude` 命令模拟 Claude 实例，zoxide 项通过实际 `cd` 进入过的目录让 zoxide 自然索引。

| fixture                          | 构成                                                                                                                                                                                                                                                                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **fixture-多状态会话组**         | `demo-a`：3 个 window，用 `tmux new-window -n <名>` 显式指定窗口名（1 号名为 `claude`，跑 Claude Code 且为活动 window；2 号名为 `server`，跑一个常驻命令模拟服务进程；3 号名为 `shell`，纯 shell）；`demo-b`：1 个 window（名为 `claude`，跑 Claude Code，idle）；`demo-c`：2 个 window（均为普通 shell，不跑 Claude） |
| **fixture-全局无Claude环境**     | **当前不存在任何 Claude 实例**：先退出 / kill 掉 `demo-a`、`demo-b` 里正在跑的 Claude 进程，只保留 `plain-x`、`plain-y` 两个纯 shell 会话（`demo-c` 本身不跑 Claude，可保留）                                                                                                                                          |
| **fixture-ATTN会话**             | 在 `demo-a` 的 1 号 window 里让 Claude 跑完一轮任务后不再需要立即输入，产生粘性 ATTN 标记                                                                                                                                                                                                                              |
| **fixture-zoxide非tmux项**       | zoxide 历史记录中一个当前没有对应 tmux session 的目录                                                                                                                                                                                                                                                                  |
| **fixture-目录名疑似window格式** | zoxide 或 configs 列表中存在一个名字形如 `sample:1` 的项，其中 `sample` 不是任何当前真实存在的 tmux 会话名                                                                                                                                                                                                             |
| **fixture-数据滞后场景**         | picker 已打开、`demo-a` 的 window 列表已被读入内存后，不重开 picker，从另一个终端把 `demo-a` 的某个 window（或整个会话）关闭                                                                                                                                                                                           |
| **fixture-宽窄终端两态**         | 同一套会话数据分别在 ≥102 列（如 120 列）与 <102 列（如 80 列）的终端窗口下打开 picker                                                                                                                                                                                                                                 |

## 1. A 类 · 可自动化用例（Go 单元测试能覆盖）

### 1.1 可见行构建

- tc-a1-p1-数据测试：折叠态下可见行序列等于过滤后的会话数
  - pc：给定过滤结果为 3 个会话，其中没有会话处于手动展开集合或搜索临时展开集合中
  - 按该输入重新构建可见行序列
    - 期望：可见行共 3 行，全部为 session 行，顺序与过滤结果一致，不包含任何 window 行

- tc-a2-p1-数据测试：单会话手动展开插入对应 window 行
  - pc：给定过滤结果为 3 个会话，第 2 个会话在手动展开集合内，其 window 表含 3 个 window（序号 1/2/3）
  - 按该输入重新构建可见行序列
    - 期望：可见行共 6 行，顺序为：会话 1、会话 2、会话 2 的 window 1、window 2、window 3、会话 3

- tc-a3-p2-数据测试：展开集合内但 window 列表为空时不产生 window 行
  - pc：给定某会话在手动展开集合内，但其 window 表为空（如会话已消失，展开记录残留）
  - 按该输入重新构建可见行序列
    - 期望：该会话下不插入任何 window 行，外观与折叠态一致

- tc-a4-p2-数据测试：window 行携带正确的所属会话与序号信息
  - pc：给定会话「proj-b」处于展开态，其 window 表为 [1: claude（活动）, 2: server, 3: shell]
  - 按该输入重新构建可见行序列
    - 期望：紧随会话行之后的 3 行依次对应 window 序号 1、2、3，且序号 1 携带活动 window 标记，其余不携带

- tc-a5-p1-数据测试：window 行不渲染徽章列也不留空占位
  - pc：给定一个已展开会话及其 window 表
  - 生成该 window 行的渲染内容
    - 期望：渲染内容不包含 ATTN/IDLE/RUN/WAIT 四列的任何字符（既不显示徽章也不留空白占位），整行从缩进起点直接开始是序号与名称

- tc-a72-p2-数据测试：window 行内容格式为「序号: 名称」，光标标记占位与 session 行一致
  - pc：给定某会话展开，其 window 表含序号 1、名称「claude」的一项；假设光标当前正停在该 window 行上
  - 生成该 window 行的渲染内容
    - 期望：该行渲染串形如 `└ 1: claude`（序号与名称间以冒号分隔）；光标标记列与 session 行占用同样的两列宽度，不因是 window 行而收窄或消失

- tc-a6-p2-数据测试：会话层排序与 window 行排序互不干扰
  - pc：给定过滤结果含一个 ATTN 触发会话与若干普通会话（乱序输入），其中一个非 ATTN 会话展开且其 window 表本身是乱序的
  - 按该输入完成排序与可见行构建
    - 期望：会话层排序仍是 ATTN 触发的会话排前、其余保持取数顺序；该会话下的 window 行按序号升序排列（不管 window 表原始顺序），且不参与会话层排序、始终紧随所属会话

### 1.3 可见行重算触发点

- tc-a11-p2-功能测试：取数完成后可见行基于最新数据重建

    - 期望：可见行变为 3 行，新增的第 3 行对应 proj-c，不沿用取数前只有 2 行的旧结果

    - 期望：可见行按新搜索词重新生成，命中会话所在行下方插入其命中的那一个 window 行，可见行总数由 3 行变为 4 行

### 1.6 预览防抖与双序号校验

## 4. 待澄清 / PRD 未定义项

1. **折叠记忆文件名未定义**：PRD 与详设都只给出了文件内容结构（`{"version":1,"expanded":[...]}`）和存放位置（与 attention.json 同目录、独立文件），没有写具体文件名。用例中一律用「折叠记忆文件」指代，不编造文件名；验收时按「与 attention.json 同目录下的独立 JSON 文件，通过目录查找定位」这一**临时口径**处理。

2. **预览各类占位 / 说明文案的具体措辞未定义**：读取中占位（PRD「预览・读取中」）、抓屏失败说明、非 tmux 项无真实会话说明、空结果态无目标说明，PRD / 详设均只规定了语义要求，没有锁定具体文案。用例判定统一降级为「非空、语义正确即可」，不断言具体文字。

3. **window 活动标记的具体符号未定义**：PRD 示意图里用 `*` 标注活动 window（`└ 1: claude *`），但 PRD 明确说明示意图「非最终视觉稿，字符级排布待实现时可微调」，详设也只说「加一个标记符」，未锁定具体字符。用例判定降级为「存在某种可识别的标记符，不要求特定字符」。

4. **`Ctrl-r` 在非 tmux 项上的行为未定义**：按键总览表只写了 `Ctrl-r` 是「重取当前预览快照」，没有说明光标停在非 tmux 项（本身就无预览目标）时按 `Ctrl-r` 该如何反应。验收时按「参照 `→` 键对非 tmux 项的无反应处理，非 tmux 项没有可重取的预览目标，`Ctrl-r` 预期也无反应」作为**临时口径**处理，但这是推断，不是文档明确要求，未纳入正式用例编号，仅供开发 / QA 参考。

5. **手动展开与搜索临时展开两态叠加时的可见行渲染优先级未定义**：若某会话已被手动展开（渲染全部 window），此时搜索又命中其下某个 window 名，可见行应渲染「全部 window」还是「只渲染命中的 window」——PRD「搜索命中 window」一节只定义了「会话名命中 + window 命中同时发生」的优先级，没有覆盖「手动展开 + 搜索命中」两个状态源叠加的情况。验收时按**临时口径**「只要出现搜索命中，无论该会话是否同时处于手动展开，均只渲染命中的 window 行」处理（因为搜索规则的措辞更具体），未纳入正式用例编号。

6. **「重复目标不重取」中「同一目标」的判定边界未定义**：光标离开又返回同一目标时沿用已取快照，但没有说明这个「返回」是否有时间窗口限制（例如离开几秒后再回来是否还算「重复目标」）。已有的 tc-a37 只覆盖了「已有快照直接沿用」的主干情形，未覆盖边界时间窗口，留待开发确认实现口径。

7. **活动 window 缺失且 window 表也为空时的展示方式未明确**：详设写明「活动 window 缺失时退回该会话的首个 window；window 表为空则按非 tmux 项处理」，但对「window 表非空、但没有任何一项标记为活动 window」这种异常数据（例如数据滞后导致活动标记丢失）具体退回到哪一个 window 只说了"取首个"，没有说明如果连"首个"的语义也存在歧义（如 window 表本身乱序未排序时"首个"是序号最小还是原始顺序第一个）时如何处理。验收时按「window 表已按序号升序排列后的第一项」作为临时口径，该口径已体现在 tc-a74 的期望结果中，仍需开发确认是否与实现口径一致。

8. **抓屏失败 / 数据滞后切换失败的提示展示形式未定义**：详设只要求「显示一行简短说明」「提示，不崩溃」，没有规定是列表内联提示、状态栏提示还是弹层提示。用例判定统一降级为「有可见的提示文案即可，不强制具体展示位置」。
